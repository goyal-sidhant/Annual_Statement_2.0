### 8.2 Why this framework and these libraries

#### 8.2.1 Tkinter for the windows (D1)

- **What the code does (READ).** Every window, tab, dialog and pop-up is Tkinter/ttk: the main window (`gui/main_window.py:9-10, 48`), the four tabs (`gui/tabs/*.py`), the widgets (`gui/widgets/*.py`), the extractor panel and its standalone window (`power_query_extractor/gui/extractor_window.py:5-6, 98, 1032`), and even the install offer (`utils/dependency_installer.py:96-97`). The theme is ttk's built-in `'clam'` (`gui/main_window.py:57-77`; `power_query_extractor/gui/extractor_window.py:85-95`).
- **Likely reason — MEDIUM.** Tkinter ships inside the normal python.org Windows installer, so nothing has to be installed for the window itself, and it is the toolkit AI chat answers most often produce for small desktop tools. The code was written through AI chats: "Author: Advanced AI Assistant" (`main.py:5`), and paste markers such as "# ADD THIS LINE" (`utils/helpers.py:17`) and "# Rest of your code remains same..." (`power_query_extractor/core/report_processor.py:295`) (READ, HIGH that it was AI-assisted). Nothing in the code or history states why Tkinter was picked; the pre-git history (19-06-2025 to 31-08-2025) is lost (HS 1.16).
- **History (READ).** The first GUI was one large file `gui/app.py` (89,275 bytes, last edited 25-06-2025) that was never committed; only its compiled files were (in edac6a3, shared - before the split on 30-10-2025; HS 1.16, DCP 4.3). It was split into the modular GUI on 23-07-2025 (`gui/main_window.py:4` "Modularized version - ties all components together"). After the split A kept Tkinter through all 34 of its own commits (project B moved to PyQt5; that is for the later comparison).
- **Comparison with the author's Standard 12 (fact only).** Standard 12 names PySide6 (Qt 6) for "Desktop windows and animations" (`rebuild_pipeline_FINAL.md:833`). A uses Tkinter. Which toolkit the merged app uses is the author's decision.
- **Costs of the choice that are visible in the code (READ):** Windows-only fonts typed into each widget (`'Segoe UI'`, `'Arial'`, `'Consolas'`; 9.5.3); a hand-built dark mode with four follow-up fixes (8.4.14, A-F28); Windows-style mouse-wheel events only (A-G68); Tk is not thread-safe, which the code has to work around (8.7 P5).

#### 8.2.2 Excel through COM (pywin32) for reports and refresh (D2)

- **What the code does (READ).** Step 3 writes the template copy's `Links` sheet through Excel itself when `platform.system() == 'Windows'` and `win32com.client` + `pythoncom` import (`core/excel_handler.py:19-28, 90-95, 104-260`). Step 4 refreshes and reads the reports only through Excel (`power_query_extractor/core/report_processor.py:20-36, 62-77, 209-415, 527-636`).
- **Reason — HIGH.** Stated in the code: "WINDOWS VERSION - Uses Excel COM to preserve Power Query and all Excel features" (`core/excel_handler.py:2-3`, unchanged since edac6a3, shared - before the split on 30-10-2025) and "Without Excel COM, report creation silently falls back to openpyxl, which does not preserve Power Query - so the ITC and Sales reports come out stripped of the queries that make them useful … Producing damaged reports is worse than refusing to start" (`utils/requirements_check.py:49-56`, be6418c, A only (after the split)). The README of the first commit says "The Excel corruption issues from previous versions have been specifically addressed" (`README.md:254@edac6a3`), i.e. an earlier (pre-git) version damaged files — MEDIUM-HIGH that this is what pushed the switch to COM (HS 6). RAN (XL E1): A's openpyxl path really drops the DataMashup part and the connections of a template.
- **Comparison with Standard 12 (fact only).** Standard 12 says a workbook with Power Query that the app writes into or refreshes must be handled by Excel through COM (`rebuild_pipeline_FINAL.md:828`) — A agrees on the choice. How A drives Excel differs from Standard 12's "Excel through COM" rules in many points (separate Excel via `DispatchEx`, `IgnoreReadOnlyRecommended` — A passes it only in Step 4's last-resort open, `power_query_extractor/core/report_processor.py:777-783`, and never checks `workbook.ReadOnly` (READ, grep) —, `RefreshAll` + `CalculateUntilAsyncQueriesDone`, `CoUninitialize` after the function returns); the point-by-point check is XL §3 and Section 7 (A-G3, A-G28, A-G54, A-G79). Step 4's value READING (`_extract_data`) also uses COM although Standard 12 says reading a Power Query workbook with openpyxl is fine (`rebuild_pipeline_FINAL.md:827`) — fact only.

#### 8.2.3 openpyxl for everything without Power Query (D3)

- **What the code does (READ).** openpyxl creates the five-sheet Step 3 summary workbook (`core/excel_handler.py:371-409`) and the Step 4 consolidated workbook (`power_query_extractor/core/data_consolidator.py:20-186`) from scratch, and is the fallback for the ITC/Sales reports when COM is not available (`core/excel_handler.py:96-102, 262-322`).
- **Reason — HIGH.** Those two workbooks are new files that hold no Power Query, so they do not need Excel; openpyxl also works off Windows. The fallback exists so Steps 1-3 can run on a non-Windows PC ("Fallback to openpyxl if not on Windows", `core/excel_handler.py:30`), at the price of losing Power Query, which the code only logs ("Not on Windows - Power Query may not be preserved!", `core/excel_handler.py:96-102`). Since be6418c (A only (after the split)) the start-up check blocks that fallback on Windows (`utils/requirements_check.py:57`), but not when pywin32 is present-but-broken (A-G7, RAN XL E2).
- **Standard 12 (fact only).** Standard 12 says: never let openpyxl save over a workbook with Power Query; check for a `DataMashup` part first (`rebuild_pipeline_FINAL.md:846-850`). A has no such check anywhere (READ, grep for "DataMashup"/"customXml": none in non-test code).

#### 8.2.4 lxml

- **What the code does (READ + RAN me).** No A file imports lxml (RAN me: an AST list of every import in the 43 program files, inline command listed in 9.11; table in 9.1). It is listed as "Optional but recommended for better performance" (`requirements.txt:11-12`). openpyxl uses it by itself whenever it is installed: `LXML = lxml_available() and lxml_env_set()` with `OPENPYXL_LXML` defaulting to `"True"` (`openpyxl/xml/__init__.py` of the installed openpyxl 3.1.5); RAN me: `openpyxl.xml.LXML` = True in venv-A (`out_s5_imports.txt`).
- **Reason — MEDIUM.** Faster writing of the summary/consolidated workbooks. Listed since the first commit (`requirements.txt@edac6a3`).

### 8.3 Why the code is structured this way

#### 8.3.1 Two programs that became one, with one extractor and two hosts (D15)

- **What the code is (READ).** A has two entry points: `main.py` (the organiser, Steps 1-4) and `launch_extractor.py` (the Power Query Extractor alone). The extractor lives in its own package `power_query_extractor/` with its own `config/`, `core/` and `gui/` sub-packages and its own log file (`power_query_extractor/extractor_main.py:12-19`). Since a677670 (A only (after the split)) its whole UI is `ExtractorPanel(ttk.Frame)` (`power_query_extractor/gui/extractor_window.py:98`), hosted either by the thin standalone window `PowerQueryExtractorApp(tk.Tk)` (`:1032-1063`) or by the Step 4 tab (`gui/tabs/extract_tab.py:74-80`, bfcb24a, A only (after the split)).
- **Reason — HIGH.** Stated in the design note: the two programs "communicate only through `~/.gst_organizer_cache.json`" and running them separately "makes the normal end-to-end job feel disjointed" (`docs/superpowers/specs/2026-07-25-merge-extractor-design.md:8-17`); the goal was "One implementation, two homes" (`:43`) under the hard constraint "the app works today and must not break" (`:19-21`). Why it was a separate program in the first place: the older audit's D3 says "the user may want to run the extractor days later or multiple times" (`PROJECT_AUDIT_ANNUALSTATEMENT.md:683-684`) — MEDIUM (the older audit's own inference), and the design note keeps Step 4 "always accessible, with its own folder picker" for that reason (`docs/superpowers/specs/2026-07-25-merge-extractor-design.md:29, 85-89`).
- **Consequences visible in the code (READ).** Window-level settings (title, size, global ttk styles) moved into the shell because "ttk styles are application-global" (`power_query_extractor/gui/extractor_window.py:85-95, 1032-1039`; a677670 message). The Step 4 tab imports `extractor_window`, not `extractor_main`, so the second `logging.basicConfig` does not "hijack the main app's logging" (`gui/tabs/extract_tab.py:8-10`). The design note's plan to move that `basicConfig` call out of `extractor_main.py` (`docs/superpowers/specs/2026-07-25-merge-extractor-design.md:54-56`) was side-stepped instead of done (`power_query_extractor/extractor_main.py:12-19` still configures logging at import; RAN me `out_s7_extractor.txt`: importing it creates `pq_extractor.log` in the current folder). The extractor package is no longer self-contained: since ba2a753 (A only (after the split)) it imports the main app's `utils.excel_com` (`power_query_extractor/core/report_processor.py:39`), so it needs the program folder on the search path (9.5.2).

### 8.4 Why some things are done in a complex way, and the likely domain reason

#### 8.4.1 The Power Query refresh by key presses and fixed waits (D4; A-F21, A-R71, A-R72)

- **What the code does (READ; cannot run here).** For each report copy: `Dispatch("Excel.Application")` (`power_query_extractor/core/report_processor.py:218`); `Visible = True` "Keep it visible to avoid issues", `DisplayAlerts = False`, maximised (`:225-227`); open; wait 5 × 1 s ("Increased from 3 to 5", `:253`); bring Excel to the front with `WScript.Shell.AppActivate` up to 3 times and "continuing anyway" if that fails (`:258-276`); press `"%a"`, `"r"`, `"a"` one second apart ("Increased from 0.5", `:281-293`) = Alt+A, R, A = Data → Refresh All in English Excel ⚠; wait the configured seconds (`:297-302`); look for error dialogs (`:305-342`); wait `max(10, wait_time)` more (`:326-330`); check `Info!BB2` (`:345`); always save (`:348-351`). No `RefreshAll`, no `BackgroundQuery`, no `CalculateUntilAsyncQueriesDone` anywhere (READ, grep).
- **Evidence that it was tuned by trial and error, before git (HIGH).** The tuning comments "Increased from 0.5", "Increased from 3 to 5" are already in the first commit (`power_query_extractor/core/report_processor.py:189, 219, 224@edac6a3`), plus "# WAIT 7 SECONDS AS REQUESTED" above a 10-second loop (`:235@edac6a3`) — the author asked for waits in a chat and the code drifted from the comment. bd176bf (shared - before the split on 30-10-2025) then made the first wait configurable (5-60 s, default 10) instead of detecting the end of the refresh (HS bd176bf).
- **Evidence that it was kept on purpose (HIGH).** The July 2026 design note lists "Rewriting the Power Query refresh itself (the SendKeys approach and its fixed `time.sleep` waits stay as they are)" as out of scope (`docs/superpowers/specs/2026-07-25-merge-extractor-design.md:125-126`).
- **Why key presses instead of Excel's own `RefreshAll` command — LOW (not recorded anywhere).** Possible domain reasons, none provable here: (a) a `RefreshAll` sent through COM returned at once while Power Query kept refreshing in the background, so the saved file held old data — exactly the failure Standard 12 records as tested ("a plain `RefreshAll()` followed at once by a save stored the old 2 rows", `rebuild_pipeline_FINAL.md:860-866`); pressing the ribbon keys and waiting "worked" visibly; (b) Power Query privacy-level or credential prompts appear only in a visible Excel, hence "Keep it visible to avoid issues" (`:225`) — LOW. **NOT SURE — how to check:** ask the author whether `RefreshAll` through COM was tried and what went wrong (shared-history question 3); on Windows, refresh one report with `RefreshAll` + `CalculateUntilAsyncQueriesDone` and compare `Info!BB2` and a figure cell with the key-press result.
- **Consequences (cross-references).** The keys go to whatever window has focus (A-G55); the refresh cannot be confirmed and is saved regardless (A-G2, A-G3); about 36 s of fixed waiting per report at the default (A-R72, A-G50); English Excel key tips assumed ⚠ (A-G44).

#### 8.4.2 Step 3 attaches to a running Excel; Step 4 uses `Dispatch` (D5; A-R97, A-R103)

- **What the code does (READ).** Step 3: `GetActiveObject("Excel.Application")` first, `Dispatch` only if that fails (`core/excel_handler.py:123-128`), then `Visible = False`, `DisplayAlerts = False`, `ScreenUpdating = False` (`:131-133`); in the clean-up the comment says "Don't quit if Excel was already open" but the test is `if self.excel_app is None` (`:241-242`) and `self.excel_app` is only ever set to `None` (`:56`), so `Quit()` is always called (`:244`). - **Likely reason — MEDIUM.** The author (or the AI) wanted to reuse an Excel that is already open, to save the start-up time of a new Excel per report and avoid many `EXCEL.EXE` processes, and to leave a user's own Excel running; the `excel_app` attribute and `__del__` (`core/excel_handler.py:56-64`) are the unfinished half of that idea (DCP 1.5, 3.6 B1; present since edac6a3, shared - before the split on 30-10-2025). ### 9.6 File-system assumptions
