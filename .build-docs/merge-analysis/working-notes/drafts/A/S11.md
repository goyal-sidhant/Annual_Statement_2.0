### 11.0 How to read this section

**What "rebuild" means here.** A rebuild that does everything A does today (the 31 features A-F1 to A-F31 and the 157 rules A-R1 to A-R157 of the registry, `/root/merge-scratch/audit/A_registry.md`), without A's known defects (the 79 gaps A-G1 to A-G79 of Section 7). Whether the merged program is built from A, from project B or from both is decided later (the comparison); nothing here chooses between A and B.

**What this section does and does not do.**
- It gives technical recommendations only: how to structure, order, test and harden the code.
- It never decides a GST rule. Anything that decides a tax figure, which return / table / sheet / cell a figure or file belongs to, a rate, limit or threshold, rounding, the financial year or tax period, GSTIN / PAN / state-code logic, ITC eligibility or reversal, or a due date is tagged **[GST RULE]**: the rebuild copies such rules exactly as the author approves them, and every improvement that touches one is limited to making the code do what the author's rule says (for example "make the cell wiring match the mapping table the author approves"). Nothing here says whether any GST rule is right.
- Values that change over time (package and Python versions, Excel behaviour and keyboard shortcuts, the ~218-character path figure, template cell positions, table numbers, file-name conventions, the state list) carry **⚠** so the author can check them.
- Where the author's own Standards 12 and 13 (`/home/user/Annual_Statement_2.0/.build-docs/toolkit/rebuild_pipeline_FINAL.md:817-898` and `:900-1061`) say something, this section states the fact and what each choice means for the rebuild; adopting a standard is the author's decision.

**The IMPORTANT CONSTRAINT of the audit method (item 4), and how it was applied.** Before any improvement was written, Section 8 (Design decisions D1 to D20, iterations I1 to I23, patterns P1 to P9) was checked for that topic. Every row of 11.4 has a "Section 8 check" column. Where Section 8 explains why A's approach was chosen over the alternative that would otherwise be obvious, the row does NOT recommend that alternative: it gives a third option that keeps the original reason, or states the trade-off honestly. These cases are collected in 11.4.3 (T1 to T10).

### 11.3 Feature priority

**Tiers.** *Tier 1 — essential*: without it the program cannot do its job (sort the clients' GST files, build the ITC and Sales reports, refresh them and bring the figures into one workbook) or cannot be run safely. *Tier 2 — important*: protects correctness, saves a lot of time or is used in every run, but the job can be done without it for a first release. *Tier 3 — nice-to-have*: convenience or appearance. The tiers are a technical view of the evidence; which features the merged program keeps is the author's decision, and "essential" says nothing about whether any GST rule inside a feature is right.

### 11.5 Estimated complexity

#### 11.5.1 How the ratings were made

**Scale (the audit method's):** SIMPLE = under 1 hour, MODERATE = 1 to 3 hours, COMPLEX = 3 hours or more, for AI-assisted rebuilding (Claude Code working from this audit as the specification).

**What one rating covers:** writing the feature in the structure of 11.1.5, its tests that can run anywhere (unit, contract and guard tests, 11.1.6), and the technical fixes 11.4 lists for it. **Not covered:** the author's decisions (11.7), preparing the shared runtime on the office share, and the time of the office-PC acceptance sessions for everything that drives Excel (they depend on the PCs and cannot be estimated from the code); the column "Office-PC test" says which features need one.

**Evidence used for each rating:**
- the size of the feature in A, counted from the registry's "Where it lives" ranges (RAN me, `s1_feature_size.py`: physical lines, and "code lines" = not blank and not a pure comment line, overlapping ranges counted once; A-F14 and A-F15 share one mechanism and are counted together). The script holds the registry's MAIN ranges, typed into it by hand: some are widened to the span between two nearby ranges of one file (for example A-F1's `utils/dependency_installer.py:23-158` for the registry's `:26-38, 41-60, 63-74, 88-158`), and single-line mentions in other files are left out (for example A-F6's `gui/main_window.py:93, 369, 386-387`, `core/file_organizer.py:30, 42, 83-87` and `gui/handlers/processing_handler.py:194`), so the "files" figure counts the files with a main range, not every file the registry names, and the sizes are approximate (READ `/root/merge-scratch/run/A-S11/scripts/s1_feature_size.py:13-78`; re-run by verification with identical output) [Corrected during verification — the approximation was not stated];
- the rules the feature carries (registry);
- the gaps the rebuild must fix in it (11.4.2's "Features" column; HIGH and MEDIUM-HIGH gaps named);
- whether it drives Excel through COM (then it can be finished only with an office-PC test);
- how often A itself had to rework it (Section 8.5, iterations I1 to I23).

**Confidence:** every rating is an inference (MEDIUM for the order between features; LOW-MEDIUM for the hours themselves). The size of a feature in A is a weak guide: A's code carries dead and duplicated parts (SR8, P4), while the rebuild adds the checks of 11.4.
