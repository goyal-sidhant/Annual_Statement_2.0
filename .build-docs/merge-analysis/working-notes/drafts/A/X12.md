**Plain-English terms used in this appendix.**

- **Workbook / template**: `.xlsx` is a normal Excel workbook, `.xltx` an Excel template, `.xlsm` / `.xltm` their macro versions. All four are ZIP files holding XML "parts".
- **Power Query** (Excel's data-import tool). Its queries live inside the workbook in a hidden part `customXml/item*.xml` that contains an element called **DataMashup**, plus connection records in `xl/connections.xml`. **Refresh** = re-running the queries so they read the source files again.
- **openpyxl** (a Python library that reads and writes `.xlsx` files without Excel). When it **saves**, it rebuilds the file from what it understands and drops the Power Query parts; reading is harmless.
- **COM** (Windows' way for one program to drive another; here Python drives Microsoft Excel). **pywin32** is the Python package that provides COM (`win32com`, `pythoncom`) and window functions (`win32gui`, `win32api`, `win32con`).
- **GetActiveObject / Dispatch / DispatchEx** (three ways for Python to get an Excel): `GetActiveObject` grabs the Excel that is already running (normally the user's own); `Dispatch` starts one but, for Excel, commonly connects to one already running; `DispatchEx` always starts a separate Excel. Standard 12 requires `DispatchEx`.
- **Visible / DisplayAlerts / ScreenUpdating** (Excel settings: is its window shown, does it show prompts such as "Save changes?", does it repaint the screen). **Quit()** closes that whole Excel with all its workbooks.
- **RefreshAll / BackgroundQuery / CalculateUntilAsyncQueriesDone / Refreshing / RefreshDate** (the COM calls and properties Standard 12 names for a safe refresh: switch off background refresh on each connection, refresh, wait until every query has finished, check none is still refreshing, never trust the refresh date).
- **SendKeys** (pressing keyboard keys by program; the keys go to whichever window has keyboard focus). **Ribbon key tips** (Excel's Alt-key shortcuts: Alt, A = Data tab; then R, A = Refresh All).
- **Thread / worker thread** (a second line of work beside the window). **Daemon thread** (a worker that is killed instantly, without its clean-up, when the program ends).
- **CoInitialize / CoUninitialize** (calls a worker thread must make before and after using COM).
- **Staging file** (a temporary local copy that is worked on and then copied to its final place). **UNC path** (a network path `\\server\share\...`). **8.3 short path** (an old DOS-style short alias of a long path). **`\\?\` prefix** (a Windows prefix that lifts the 260-character path limit for programs that support it).
- **pip** (Python's package installer; `pip install pywin32` downloads and installs a package into one particular Python). **ImportError** (the error Python raises when a package cannot be loaded).
- **find_spec** (a Python check that a module file exists, without loading it). **glob** (a wildcard file search such as `ITC_Report_*.xlsx`). **mtime** (a file's or folder's "date modified").

### X1.1 The findings that matter most (author's top priority)

> **1. Step 3 takes over the user's own open Excel, hides it, and then closes it.** `core/excel_handler.py:123-125` first calls `GetActiveObject("Excel.Application")` (the user's running Excel), and only if that fails `Dispatch` (`:126-128`). It then sets `Visible = False` (`:131`) and never sets it back (the clean-up at `:238-246` restores only `ScreenUpdating` and `DisplayAlerts`). The comment "Don't quit if Excel was already open" (`:241`) is not what happens: the test is `if self.excel_app is None` (`:242`) and `self.excel_app` is only ever `None` (`:56`; no other assignment anywhere, READ by search), so `excel.Quit()` (`:244`) is called **every time**. Just before it, `:240` switches `DisplayAlerts` back to `True`. RAN (fake COM, R2 scenario a): the call order is `GetActiveObject` → `Visible=False` → ... → `DisplayAlerts=True` → `Quit()` with the user's unsaved workbook still open. What a real Excel then does (the user's windows vanish; Excel either closes or waits on an invisible "Save changes?" prompt, which would also block the Step 3 worker) is READ, MEDIUM-HIGH, untestable here. Present since the first commit `edac6a3` (shared - before the split on 30-10-2025) and unchanged by A. See A-R97, A-F14, A-F15.

> **2. Step 4 does not use `RefreshAll` at all: it presses keys in a visible Excel and then always saves.** `power_query_extractor/core/report_processor.py:278-293` sends `SendKeys("%a")`, `"r"`, `"a"` (Alt+A, R, A ⚠) to whichever window has focus, after trying to bring Excel to the front (`:260-276`, and it carries on even if that failed, `:273-274`). It then waits fixed times and saves (`:349`) whether or not an error dialog appeared or the success check failed. No `BackgroundQuery`, `RefreshAll`, `CalculateUntilAsyncQueriesDone` or `Refreshing` exists anywhere in A (RAN search). The design note keeps this on purpose ("the SendKeys approach and its fixed `time.sleep` waits stay as they are", `docs/superpowers/specs/2026-07-25-merge-extractor-design.md:125-126`). RAN (fake COM, R3): 39 seconds of fixed waiting per report at the default 10-second wait. See A-R71, A-R72, A-F21.

> **3. Step 4 uses `Dispatch` (not `DispatchEx`) twice per report and quits whatever it got.** `report_processor.py:218` (refresh, made visible and maximised `:225-227`) and `:536` (extraction, hidden `:537`), each ending with `Quit()` (`:406`, `:628`). If `Dispatch` attaches to the user's running Excel (MEDIUM-HIGH, general pywin32/Excel behaviour and the premise of Standard 12; cannot be tested here), that Excel is maximised, driven by keystrokes and then quit with `DisplayAlerts = False`, which by Microsoft's documented behaviour closes without asking about unsaved work. RAN (fake COM, R3 scenario b): `Quit()` is called on the attached Excel while its unsaved workbook is still open. See A-R103.

> **4. A failed refresh is saved under the "_Refreshed_" name and later trusted.** If the refreshed copy cannot be opened, the copy made at `report_processor.py:164` stays in the Version folder under the refreshed name; "Skip Refresh" (`:137-155`) then reuses the newest such file and reports `success: True` ("Skipped - Using existing refreshed file"). RAN (fake COM, R3 scenarios f and f2): the second run marks the never-refreshed copy ✓ and its values reach the consolidated workbook. See A-R69, A-F22.

> **5. The only proof of a successful refresh is "`Info!BB2` is not empty, not 0, not an error"** (`report_processor.py:638-685`) [GST RULE] ⚠ — it cannot tell a new value from one already in the file. `RefreshDate` is never used (MET). See A-R73.

> **6. The openpyxl fallback silently strips Power Query and still reports success.** RAN (R1): on Linux, A's own `create_report_from_template` returned `True` for both reports while the output had lost `customXml/item1.xml` (DataMashup), `customXml/itemProps1.xml`, `customXml/_rels/item1.xml.rels` and `xl/connections.xml`. No DataMashup check exists anywhere in A (RAN search). On Windows the start-up check (added in `f363946` and made blocking in `be6418c`, both A only (after the split)) blocks a *missing* pywin32, but it checks only that a `pythoncom` file exists (`utils/requirements_check.py:64-70`), while Step 3 needs `import win32com.client` **and** `import pythoncom` to succeed (`core/excel_handler.py:21-28`). RAN (R4, simulated broken pywin32 on "Windows"): start-up check passes, Step 3 falls back to openpyxl. See A-R96, A-R124.

> **7. Nine columns of the consolidated workbook show a different cell's value from the one the configuration names** — a technical mismatch between configuration and code; which cell is right is the author's call [GST RULE] ⚠. RAN (R3): in `PQ_Extraction_Report_*.xlsx` the IGST/CGST/SGST columns of "IMS Reco", "Extra In Purchase" and "Extra In GSTR2B" received the markers placed in `Diff GSTR-3B!J15/K15/L15`, not those in `IMS_Reco!AA1/AD1/AG1`, `ExtraInPurchase!O1/P1/Q1`, `ExtraInGSTR2B!S1/T1/U1` (the original R3 printout showed only the first two sheets; the verification re-run printed all three and confirmed "Extra In GSTR2B" too). > **8. Nothing stops Step 3 and Step 4 driving Excel at the same time, and closing the window during Step 4 kills the worker without its clean-up.** Step 3's flag `app.is_processing` (`gui/handlers/processing_handler.py:71-76, 124, 528`) and Step 4's own `ExtractorPanel.is_processing` (`power_query_extractor/gui/extractor_window.py:119, 872, 962`) never check each other; both workers are daemon threads (`processing_handler.py:129-133`, `extractor_window.py:878-883`); the close handler asks only about Step 3 (`gui/main_window.py:344-355`). READ, HIGH for the code; what a real Excel is left doing is MEDIUM.

> **9. Originals are never modified.** Client input files are only read (8 bytes) and copied (`utils/helpers.py:282-283, 199`); templates are only copied (`core/excel_handler.py:154, 279`); Step 3 reports are copied before Step 4 touches them (`report_processor.py:164`). READ (search for remove/unlink/rename/move/rmtree: every hit is on a copy, a staging file or something the app made) and RAN (R1: templates and inputs unchanged). HIGH. No code anywhere kills an Excel process (no `taskkill`, `psutil`, `os.kill`, `TerminateProcess`; RAN search).
