### 6.1 Overview in plain words

Project B is written in a "catch it and carry on" style. It has 91 `except` handlers in 90 `try` statements, and none of them is a bare `except:` (RAN (me), `scripts/try_inventory.py`, output `out/inv.tsv` and `out/inv.err`; the count matches DC P-02). The three long jobs - scanning, processing and extraction - each run in a worker thread, and each worker catches every error and reports it to the window, which shows a message box (READ: `gui/controllers/scan_controller.py:39-41`, `gui/controllers/processing_controller.py:38-40`, `gui/controllers/extraction_controller.py:39-41`; boxes at `gui/pyqt_main_window.py:318-322`, `:412-415`, `:563-565`). Inside the jobs, errors are contained at the level of one file, one client or one report, so one bad item rarely stops the batch.

The other side of this style is that many problems are only written to the program log file, which the user rarely opens, or are swallowed completely, and the job still ends with a success message. Section 7 lists where that hides wrong results. This section lists what B does handle.

### 7.0 How to read this section

Each gap has an ID (B-G1 … B-G82), the place in the code, what happens, how the user notices (or does not), a severity, the evidence and the related registry IDs. 7.7 is the silent-bug scan the audit method asks for (closures, mutable defaults, off-by-one and so on); 7.8 runs the "what would break if…" scenarios for every major feature and points back to these IDs; 7.10 lists all IDs in one table. Evidence words, note names and the [GST RULE] / ⚠ markers are explained in 6.0.

**Severity scale used here.**
- **HIGH** - can silently produce wrong figures or wrong files, lose the user's work, damage a workbook, act on other programs, or stop normal use, in situations that happen in ordinary office work.
- **MEDIUM** - wrong, misleading or failed output in plausible but less common situations, or a significant obstacle the user can work around.
- **LOW** - cosmetic, rare, latent (needs a configuration change to bite) or only a maintenance trap.

Severity describes the technical consequence. For anything tagged [GST RULE], only the mechanism is described: whether the rule itself is right is the author's decision, and "which cell is right" is always the author's call.

### 7.1 Missing validations that could silently corrupt data

#### B-G1 - The consolidated Step 4 workbook fills 9 of its 22 figure columns from a cell other than the one its configuration names [GST RULE] ⚠

- **Where:** `power_query_extractor/core/data_consolidator.py:125-138` (the look-up), fed by `power_query_extractor/core/report_processor.py:536-539` (each value stored under its field name and its bare cell address) and `power_query_extractor/config/cell_mappings.py:255-278` (field names built as "<output sheet>_<output column>" with spaces turned into "_"); the three affected output sheets are configured at `power_query_extractor/config/cell_mappings.py:155-228`.
- **What happens:** for each output column the consolidator first takes the FIRST extracted field whose name merely CONTAINS the column title (`:130-133`), even if that value is empty, and uses the exact field name only if the result is None (`:136-138`). Titles with a space ("Diff IGST", "IGST Diff", "Taxable Value", "Table 6J Match" ⚠) never match an underscore field name and fall through to the exact name, as configured. The one-word titles "IGST", "CGST", "SGST" of the output sheets "IMS Reco", "Extra In Purchase" and "Extra In GSTR2B" match `GSTR-3B_Difference_Diff_IGST/CGST/SGST` first, because "GSTR-3B Difference" is the first group in the configuration. Those 9 cells therefore show the values read from `Diff GSTR-3B!J15/K15/L15` ⚠ instead of their configured cells `IMS_Reco!AA1/AD1/AG1`, `ExtraInPurchase!O1/P1/Q1`, `ExtraInGSTR2B!S1/T1/U1` ⚠ (B-R79, B-R80, B-R81, B-R83). Two more details: the figure written depends on the ORDER of the extracted data (with the same data in reverse order, six columns showed the `ExtraInGSTR2B` cells instead); and if the Diff GSTR-3B cell holds an empty TEXT (''), the exact-name fallback is skipped too and the column shows "Missing" although its own cell has a value (only None triggers the fallback).
- **How the user sees it:** not at all. The workbook looks complete; the three sheets repeat the GSTR-3B difference figures client by client.
- **Severity:** HIGH (silent figures taken from cells other than the configured ones, in a delivered workbook).
- **Evidence:** RAN (me r3, marker values that name their own source cell: "as_configured 13 of 22", the 9 differences listed one by one; reversed order: 16 of 22, the 6 differences come from `ExtraInGSTR2B`); RAN (me t1: empty text in J15 → "Missing" in the IMS Reco IGST column; None in J15 → the configured `IMS_Reco!AA1` appears); also RAN by LT §4.6, DC T3, XL E5, OF t7 and the registry's check1.py.

### 7.5 Security concerns

B stores no password or token and uses no network library (RAN, DO R97). Its security risks come from how it drives Windows and Excel, and from where it copies client data.

#### B-G61 - The error-dialog closer looks at every window on the desktop and clicks "OK", "Close", "Yes" or "Continue" in any program

- **Where:** `power_query_extractor/core/report_processor.py:368-404` (every visible, enabled top-level window whose title contains "microsoft excel", "error", "problem", "cannot", "failed", "unable", "could not", "exception", "invalid" or "missing", with a dialog class `#32770`, `NUIDialog` or `bosa_sdm_msword`), `:443-476` (clicks the first button whose text CONTAINS "ok", "close", "yes" or "continue", otherwise sends a close message).
- **What happens:** the check is not limited to B's own Excel.
