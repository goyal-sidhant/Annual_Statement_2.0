**What "rebuild" means here.** A rebuild that does everything B does today (the 34 features B-F1 to B-F34 and the 144 rules B-R1 to B-R144 of the registry, `/root/merge-scratch/audit/B_registry.md`), without B's known defects (the 82 gaps B-G1 to B-G82 of Section 7). **What this section does and does not do.**
- It gives technical recommendations only: how to structure, order, test and harden the code.
- It never decides a GST rule. #### 11.2.4 Two rules for the order of work

1. **Pure before Excel, Excel before windows.** Everything in Phases 0-2 can be tested on any computer; Phases 3-4 need an office PC; Phases 5-7 are only presentation. This keeps the risky Excel work small and well defined (MEDIUM, an engineering inference from the shape of B's code and its gaps).
2. **The characterization tests against B come before any fix.** Every intended change from B (each row of 11.4.2 that changes a result) is then visible as a failing characterization test that the author approves or rejects, instead of a silent difference. This is how lesson 2 of 12E.6 ("a rewrite needs a feature list") is applied to behaviour as well as features (HIGH that B's rewrite lost behaviours silently: at least twelve v3 behaviours disappeared in `c258047` / `a62d3cc`, both B only (after the split), 12C.5).

Tier 3 (nice-to-have): convenience, appearance or one-time use; B itself shows that several of these are barely used (a button with no receivers, an option no screen can switch on). **Outline of SK12, "One naming rule, one finder"** (the lesson B's history paid for three times):

```text
---
name: one-naming-rule-one-finder
description: Use whenever code creates file or folder names that other code (or a later run) must find again.
---
# One naming rule, one finder

## Rule
Every kind of name (run folder, version folder, report, refreshed copy, backup, history key)
has ONE module with three functions:
  make(parts) -> name          # the only way the name is created
  parse(name) -> parts | None  # the only way the name is recognised; None = not ours
  newest(names) -> name        # chooses by parsed DATE, never by text order
Writers call make(); every reader calls parse()/newest(). No glob pattern or string
search for these names anywhere else (a guard test greps for it).

## Dates in names
- A name may show the date day-first (DDMMYY HHMM) for people, but no code sorts the text.
- newest() parses the date; names that do not parse are returned separately, never "won".
- Clashes in the same minute get a counter, never an overwrite.

## User-editable parts (suffixes)
- Validated: not empty, contains the time-stamp placeholder, no characters Windows forbids.
- make() and parse() both read the same current value.

## Success is a record, not a name
- "Refreshed", "done", "processed" come from a manifest written when the step succeeded,
  not from the existence of a file whose name looks right.

## Tests (required)
- round trip: parse(make(p)) == p for every kind of name
- newest() across a month end and a year end (e.g. 311225 1000 vs 211026 0335)
- a folder copy made in Explorer ("<name> - Copy") is not chosen as newest
- a refreshed copy is never mistaken for a base report
- writer and every reader run on the same made-up folder tree (contract test)

## Evidence that this matters
- Refreshed-copy suffix made by one rule and searched by another (bd176bf, shared - before the split on 30-10-2025)
- Extract-tab folder key (c258047) and run-history keys (c258047, 7e09e5c, b0e7d0e) - all B only (after the split)
- Day-first names sorted as text for "latest" (the shared Tk extractor's Version folders, 47a1492, shared - before the split on 30-10-2025; 7e09e5c and b0e7d0e, B only (after the split))
```
