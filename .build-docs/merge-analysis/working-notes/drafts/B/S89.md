Plain-English terms used in this section (each is also explained where it first matters):

- *Framework / library*: ready-made code a program builds on. *Window toolkit*: the library that draws windows and buttons (Tkinter, PyQt5, PySide6).
- *COM*: the Windows mechanism by which one program (here Python) remote-controls another (here Excel). *pywin32*: the Python add-on package that gives access to COM and to other Windows functions (its parts are called `pythoncom`, `win32com.client`, `win32api`, `win32con`, `win32gui`).
- *Dispatch / DispatchEx / GetActiveObject*: three pywin32 ways of getting an Excel. `GetActiveObject` grabs an Excel that is already running (normally the user's own); `Dispatch` asks for "an Excel" and may be handed a running one; `DispatchEx` always starts a separate new Excel (what the author's Standard 12 asks for).
- *SendKeys / AppActivate*: Windows Script Host functions; `AppActivate` tries to bring a window to the front, `SendKeys` types keystrokes into whatever window has the keyboard focus, as if a person pressed them. *Key tips*: Excel's ribbon keyboard shortcuts (Alt, then letters).
- *Power Query*: Excel's built-in data-import feature; its queries live inside a workbook and are re-run by "Refresh All".
- *openpyxl*: a Python library that reads and writes `.xlsx` files without Excel; when it saves an existing workbook it silently drops Power Query (Standard 12, `rebuild_pipeline_FINAL.md:827`).
- *Thread / worker thread*: a second line of work running at the same time, so the window does not freeze. *QThread*: Qt's thread object. *Signal / slot*: Qt's message from one object to a function in another.
- *Module / package*: a `.py` file / a folder of modules with an `__init__.py` file. *Re-export*: an `__init__.py` that imports names from its sub-modules so that other code could write `from utils import X`. *`__all__`*: the list of names a package offers that way. *Facade*: one object or function that hides several others behind a simple front.
- *Import guard*: wrapping an import in `try/except ImportError` or a platform check, so that a missing package or a different operating system does not stop the program.
- *Dataclass*: a Python class used mainly to hold named fields. *JSON*: a plain-text file format for settings.
- *Constant*: a value written once with a name (for example `FILE_PATTERNS`) instead of being typed wherever it is needed. *Magic value*: a value typed directly into the logic.
- *Glob*: a wildcard file search such as `ITC_Report_*.xlsx`. *mtime*: a file's or folder's "last modified" time. *Stem*: a file name without its extension.

### 8.2 Why this framework and these libraries

#### 8.2.1 Python

- **What the code shows.** Every program file is Python (38 `.py` files, 7,805 lines: `/root/merge-scratch/audit/B_files.txt`; RAN (me) `compile_all.py` also counted 38). The project has been Python since the first commit `edac6a3` (shared - before the split on 30-10-2025), and compiled-file headers committed in `edac6a3` show the code was run with Python 3.12 and 3.13 between June and August 2025 (RAN (SH) §1.16).
- **Inference.** Python was the author's default from the start; the later Standard 12 makes this explicit ("Python is the default for every app", `rebuild_pipeline_FINAL.md:819-823`). **HIGH.**

#### 8.2.2 The window toolkit: Tkinter until the split, PyQt5 since `c258047`

- **What the history shows.** The shared program (`edac6a3` … `47a1492`) used Tkinter (Python's built-in window toolkit). B's first own commit, `c258047` (07-02-2026, B only (after the split)), rewrote the whole screen layer in PyQt5 (a Python wrapper for the Qt 5 toolkit) and `a62d3cc` deleted the Tkinter files two minutes later (RAN (H1) `git show --stat`). `c258047`, `a62d3cc` and the fix `c21f788` all carry "Co-Authored-By: Claude Opus 4.6" (READ, `git log`), so the rewrite was done in one AI-assisted session (HIGH).
- **Problems the old Tkinter code had to work around** (READ (SH) §1.3, §1.13, §0; READ (H1) Part 3):
  - buttons wired with `bind('<Button-1>')` instead of `command=` (`gui/tabs/setup_tab.py:115, 161, 199, 306, 318@47a1492`), with comments about "working mouse events" and "proper event binding" (`gui/tabs/setup_tab.py:20, 103@47a1492`) - such a button still fires when "disabled" [Corrected during verification - originally cited only `:20,103`, which are the two comments; the bindings themselves are at `:115` onwards; READ (verifier) `git show 47a1492:gui/tabs/setup_tab.py`];
  - a late-binding bug (a small inline function that reads a loop variable only later, so it sees the last value) introduced in `6237597` when worker-thread updates were wrapped in `root.after(0, lambda …)` (`gui/handlers/processing_handler.py:36-52@6237597`);
  - a 212-line "recursive widget walker" to switch dark mode (`gui/utils/dark_mode_manager.py@47a1492`);
  - a scan that froze the window (it ran on the window's own thread).
- **What the rewrite's message says it gained** (`c258047`, READ): "QThread-based background workers", "QSS stylesheet-based theming (replaces recursive widget-walking)" (QSS = Qt Style Sheets, CSS-like text that sets colours and fonts), "Signal/slot architecture replaces 305 self.app.xxx callback references".
- **Inference.** The move to Qt was made to get safe background work with screen updates, style sheets for the theme, and a cleaner structure - exactly the three things the Tkinter code struggled with. **MEDIUM-HIGH.**
- **Why PyQt5 and not PySide6 or Qt 6.** Nothing in the code or the messages says. **LOW**: a common default of the AI assistant at the time. Facts for the author (not a recommendation): PyQt5's licence is GPL v3 and its Qt library is LGPL v3 (RAN (me): `License:` fields of the downloaded wheels, 9.13); the newest PyQt5 build for Windows ships Qt 5.15.2 ⚠ (RAN (me), 9.1); Standard 12 names PySide6 (`rebuild_pipeline_FINAL.md:833`).
- **The author still wanted the old look.** `7e09e5c` (08-02-2026, B only) restyled the new screens to look like v3: "Colorful card-based layout matching the original Tkinter UI" (`gui/views/setup_view.py:3`), "Color palette matching the old Tkinter UI" (`gui/theme/theme_manager.py:9`) (READ (H2)). **HIGH** that the visual layout of v3 was valued; the toolkit change was about mechanics, not looks.

#### 8.2.3 openpyxl - only for workbooks the program creates itself

- **What the code does.** openpyxl writes the processing summary (`core/excel_handler.py:308-346`, B-F15) and the consolidated extraction workbook (`power_query_extractor/core/data_consolidator.py:20-174`, B-F23) - both brand-new workbooks with no Power Query. The template copies are filled through Excel (COM) instead (`core/excel_handler.py:95-217`). openpyxl is used on a template copy only in the fallback `_create_report_openpyxl` (`core/excel_handler.py:219-262`), which logs "Using openpyxl - Power Query content may be lost!" (`:224`) and cannot be reached through the window since `c258047` (B-R97, RAN (XL) E1).
- **Evidence of an earlier openpyxl-only version.** The file header says "WINDOWS VERSION - Uses Excel COM to preserve Power Query and all Excel features" (`core/excel_handler.py:2-3`); the README warns of "Excel file corruption - a common issue in earlier versions" (`README.md:5-7`) and lists "Excel corruption prevention" measures (`README.md:39-47`). RAN (XL) E2: B's own fallback, run on a synthetic workbook carrying a Power Query part, returned success and the saved copy had lost the query part (RAN (verifier) `scripts/pqdrop.py`: same result).
- **Inference.** A version before git made the reports with openpyxl, lost the templates' Power Query (the "corruption"), and the author moved report creation to Excel through COM, keeping openpyxl for new workbooks where nothing can be lost. **MEDIUM-HIGH.** This matches the author's later, tested rule in Standard 12 (`rebuild_pipeline_FINAL.md:827-828`).

#### 8.2.4 Excel through COM with pywin32

- **What the code does.** Three Excel sessions: Step 3 report filling (`core/excel_handler.py:95-217`), Step 4 refresh (`power_query_extractor/core/report_processor.py:165-366`) and Step 4 reading (`report_processor.py:478-587`). Windows-only window functions (`win32gui`, `win32con`) find and close error dialogs (`report_processor.py:368-476`).
- **Inference.** Only Excel can refresh Power Query and save a workbook without losing its queries, so COM is unavoidable for the templates. **HIGH.** How each session uses COM (and how far that is from Standard 12) is in 8.4.1, 8.4.2 and 8.4.6.

#### 8.2.5 lxml

- **What the code does.** `requirements.txt:10-11` lists `lxml>=4.9.0` as "Optional but recommended for better performance". No file imports it (RAN (me) import scan, 9.2). openpyxl uses it automatically when it is installed (RAN (me): `openpyxl.xml.LXML` is `True` with openpyxl 3.1.5 and lxml 6.1.3).

### 8.3 Why the code is structured this way

#### 8.3.1 The layers at the snapshot


#### 8.3.2 Two programs merged into one window (`c258047`)

- **Before.** At the split there were two programs: the organiser (`python main.py`, Tkinter, three tabs) and a separate "Power Query Extractor" (`python launch_extractor.py`, its own Tkinter window `power_query_extractor/gui/extractor_window.py@47a1492`) (READ (SH) §10.2).
- **After.** One window with four tabs; `launch_extractor.py` now only opens that window on the fourth tab (`launch_extractor.py:17-18`).
- **Clues to the reason.** The old extractor looked for the organiser's saved settings in the wrong place (a file in the start folder instead of the home folder: `power_query_extractor/extractor_main.py:38-42` versus `~/.gst_organizer_cache.json`), so its promised "auto-loads target folder from cache" (`README.md:171`) never worked (READ (SH) §1.10, defect O1). The rewrite's message says "Unified two separate apps (main organizer + PQ Extractor) into one 4-tab window" and "Auto-populates extraction tab from processing results" (READ `c258047`).
- **Inference.** One workflow (Setup → Validation → Processing → Extract), one settings store, and Step 4 knowing what Step 3 produced. **MEDIUM-HIGH.**
- **Side effect, not intended (HIGH, RAN (me) 9.5).** The extractor's unguarded Windows-only import (`report_processor.py:11-15`), harmless while the extractor was a separate program, became part of the window's start-up, so the whole program now needs pywin32 to open (B-G32, B-R124).

#### 8.3.3 New layers around an untouched core

- **What changed and what did not.** `c258047` created `models/` ("Framework-agnostic state layer (dataclasses + persistence)"), `gui/views/`, `gui/controllers/` and `gui/theme/`. It did **not** touch `utils/constants.py` (file-name patterns, folder templates, Links-sheet cells, state codes) or `power_query_extractor/config/cell_mappings.py` (which report cells are read) - READ (H1) `git show --stat c258047`: "no regex, folder template, cell mapping, state-code table or extraction mapping changed in this commit". Replaces the old Tkinter GSTOrganizerApp god object."
- **Inference.** Keep the rules that had been proven in real use and rebuild only the screens and the plumbing around them. **HIGH.** Separating state (`models/`) from screens was meant to let the state be used without the window. RAN (me) `layer_imports.py`: with PyQt5 blocked, `models.app_state`, `models.run_history`, `models.cache_manager`, `core.*`, `utils.*`, `power_query_extractor.config.cell_mappings` and `power_query_extractor.core.data_consolidator` all import; `models.signals` does not (it needs PyQt5).

#### 8.3.4 Configuration kept in Python files

- **What the code does.** All business configuration is Python: `utils/constants.py` (patterns, folder names, Links cells, modes, state codes) and `power_query_extractor/config/cell_mappings.py`, whose docstring is a user manual ("Cell Mapping Configuration - MASTER VERSION … HOW TO EDIT THIS FILE", `cell_mappings.py:1-27`) with a commented example block to copy (`:229-241`) and a "DON'T EDIT BELOW THIS LINE" marker (`:255-257`). - **Inference.** The author edits the rules with an AI assistant directly in the code rather than through a settings screen; Python dictionaries also allow comments next to each rule. **MEDIUM.** Consequence: a change needs a restart (the derived tables are built once at import, `cell_mappings.py:264-278`), and a typing mistake in the file stops the program (not checked by any test - B has none).

#### 8.3.5 The "thin" window is not thin

- **What the code does.** `gui/pyqt_main_window.py` is 608 lines and holds logic of its own: the dry run (`:326-343`, B-F11), the scan-statistics text (`:244-316`, B-F7), the disk walk that builds the Step 4 tree (`:419-504`, B-F18), the tab dots (`:567-590`, B-F29) and the completion handling (`:373-415`).

- **Inference.** Quick features were placed where the data was at hand, so the window slowly became a new god object; its docstring ("Thin", `:2`) describes the plan of `c258047`, not the snapshot. **HIGH.** Effect: the disk walk runs on the window's own thread (B-G58).

### 8.4 Why some things are done in a complex way, and the likely domain reason

Each sub-section gives: what the code does (READ unless marked), the clues, the inference with its confidence, and what it costs today (cross-references to Section 7 gaps). None of this judges a GST rule.

#### 8.4.1 Power Query refreshed by keystrokes into a visible Excel (B-F19, B-R66 to B-R69)

**What the code does**, per report, in `power_query_extractor/core/report_processor.py:165-366`:

1. `pythoncom.CoInitialize()` (`:171`), then `win32com.client.Dispatch("Excel.Application")` (`:174`) - not `DispatchEx`.
2. Up to five tries, two seconds apart, to set `Visible = True` with the comment "Keep it visible to avoid issues" (`:181`), `DisplayAlerts = False` (`:182`) and `WindowState = -4137` (maximised, `:183`); after five failures it carries on anyway (`:190`).
3. Opens the copy in up to three attempts, three seconds apart, as long as Excel answers "Call was rejected by callee" (any other error ends the open at once) (`:192-205`), then waits five seconds "to fully load" (`:207-211`, comment "Increased from 3 to 5").
4. Creates a `WScript.Shell` object (`:216`), tries three times to bring the Excel window to the front with `AppActivate(excel.Caption)` (`:218-230`), and sends `SendKeys("%a")` (Alt+A), `"r"`, `"a"` one second apart (`:236-249`, comments "Increased from 0.5"). These are Excel's ribbon key tips for Data → Refresh All → Refresh All (MEDIUM: depends on the Excel version and display language).
5. Waits the user's wait time (`:253-258`), checks five times for an error dialog (`:260-278`), waits `max(10, wait time)` more seconds (`:280-286`), checks once more (`:288-298`).
6. Checks cell Info!BB2 (`:300-301`, B-R71 ⚠), saves **whatever happened** (`:303-307`), closes with `SaveChanges=True` (`:316-319`), and in `finally` closes again, quits Excel and un-initialises COM (`:345-366`).

There is no `RefreshAll()`, no `BackgroundQuery = False`, no `CalculateUntilAsyncQueriesDone()` and no check that a connection is still refreshing (READ; RAN (XL) grep: none of these names in any `.py` file).

**Clues to the reason.**

- The method is older than git. RAN (me): in the compiled copies committed with `edac6a3`, the older one of `report_processor` (Python 3.12, source dated 25-06-2025 by its header, RAN (SH) §1.16) contains the name `SendKeys` once and `RefreshAll` zero times; the Python 3.13 copy is the same (counts only; nothing else was read from those files). RAN (me) `git log -S`: no commit of B's history ever contained `RefreshAll`, `DispatchEx` or `CalculateUntilAsyncQueriesDone`. So if a COM refresh was ever tried, it was before 25-06-2025, and the reason it was dropped is lost.
- The only comment is "Keep it visible to avoid issues" (`:181`). A refresh that Excel runs in the background returns at once; saving straight away keeps the old data - the exact problem the author later tested and wrote down in Standard 12 (`rebuild_pipeline_FINAL.md:860-867`: a plain `RefreshAll()` followed at once by a save "stored the old 2 rows"). Power Query prompts (privacy levels, missing source, credentials) are also only answerable in a visible Excel.
- The waits were tuned by trial: a "WAIT 7 SECONDS AS REQUESTED" comment sat over a ten-second loop at `edac6a3`; `bd176bf` (shared) made the wait a user setting (5-60 s, now 5-120 s, `gui/views/extraction_view.py:126-128`) "with configurable wait time" (READ (SH) bd176bf).
- The rest of the refresh code is built around the keystroke method: the error-dialog closer (8.4.7) exists because a keystroke gives no return value and Excel's error boxes would otherwise block; the BB2 check exists because nothing else tells the program whether the queries ran.

**Inference.** The author automated what a person does by hand - open the report, press Data → Refresh All, wait, save - because that reliably updated the figures in the office's Excel, while a refresh started from code either returned before the queries finished or failed invisibly. **MEDIUM** for "chosen because it worked visibly"; **LOW** for any specific earlier failure (no surviving evidence). The domain reason for refreshing at all is **HIGH**: each client's report template reads that client's organised files through the Links cells (8.4.8), so its Power Query must be re-run per client before the check figures can be read.

**Constraint any change must respect (technical, for Section 11).** The refresh must really have finished before the save; Standard 12 records that a plain `RefreshAll()` followed at once by a save keeps stale data (`rebuild_pipeline_FINAL.md:860-867`). The author's tested sequence is in Standard 12 itself; this audit does not choose between methods.

**What it costs today.** B-G6 (refresh cannot be confirmed; copy saved whatever happened), B-G51 (depends on Excel version, language, an unlocked screen and nobody touching the PC), B-G57 (about 39 seconds per report at the default wait), B-G61 and B-G62 (dialog clicking and keystrokes can reach other programs), B-G39 (nothing times out).

#### 8.4.2 Attaching to an Excel that is already running (B-R96; Step 4: B-R66, B-R101)

**What the code does.**

- Step 3 (making the reports, `core/excel_handler.py:95-217`): first `GetActiveObject("Excel.Application")` - attach to an Excel the user already has open, logging "Using existing Excel instance" (`:110-112`) - and only if that fails `Dispatch` (`:113-115`). It then sets `Visible = False`, `DisplayAlerts = False`, `ScreenUpdating = False` on that Excel (`:118-120`). In `finally` it sets `ScreenUpdating` and `DisplayAlerts` back to True (`:204-205`) and, under the comment "Don't quit if Excel was already open" (`:206`), calls `Quit()` when `self.excel_app is None` (`:207-211`). `self.excel_app` is set to `None` in `__init__` (`:55`) and never assigned anywhere (READ; DC D-29), so `Quit()` always runs - also on the user's own Excel (RAN (XL) E3 with stand-in COM objects: the user's instance was hidden and told to quit while the user's workbook was open in it).
- Both open routines first look for a workbook with the same full path already open in that Excel and reuse it (`core/excel_handler.py:273-277`; `power_query_extractor/core/report_processor.py:657-660`); the Step 4 routine's second attempt closes every workbook with the same file name without saving (`report_processor.py:692-699`).
- Step 4 uses `Dispatch` for both its sessions (`report_processor.py:174, 487`), which may also be handed a running Excel (MEDIUM; not testable here).

**Clues.** The never-assigned `self.excel_app`, the comment at `:206` and the dead `__del__` that would quit `self.excel_app` (`:57-63`) are three pieces of one plan: "reuse the user's Excel if there is one, and leave it open afterwards". Only the first piece was written. The reuse-an-open-workbook branches suggest the author met "file already open" situations. The shared run log of `edac6a3` (described by kind only) records six "Created new Excel instance" lines and no "Using existing Excel instance" line (READ (SH) §1.11), so in the logged runs no user Excel was attached.

**Inference.** Attaching was meant to avoid starting a new Excel twice per client (speed) and to avoid two Excels fighting over the same files; leaving the user's Excel open was intended but never finished. **MEDIUM** for the reason, **HIGH** that the intent is unfinished.

**What it costs today.** B-G63 (the user's Excel is hidden and closed; Step 4 may reuse it and close same-named workbooks without saving), B-G38 (if Excel dies the clean-up itself fails), B-G74 (Step 3 and Step 4 can run at the same time and both drive Excel). Standard 12 asks for `DispatchEx` and "Never take over the user's own open Excel" (`rebuild_pipeline_FINAL.md:851-855`).

#### 8.4.5 Step 4 refreshes a time-stamped copy, never the Step 3 report (B-R62)

#### 8.4.6 Two Excels per report in Step 4

#### 8.4.7 The Info!BB2 check and the error-dialog closer (B-F20, B-F26, B-R71, B-R102, B-R103)

**What the code does.** A refresh counts as successful only if no error dialog was seen and a sheet named "info" (any letter case) has a non-empty, non-zero, non-error value in cell BB2 ⚠ (`report_processor.py:589-636`; the comment at `:605` and the message at `:632` call it the "Client Name") [GST RULE]. #### 8.4.9 Copy, verify by size, never move; back up in Fresh mode (B-R42, B-R43)

#### 8.4.10 Long-path handling: the 218-character limit, 8.3 short names and `\\?\` prefixes (B-R98 to B-R100)

**What the code does.** A path longer than 218 characters is treated as too long for Excel ("Excel's typical limit", `report_processor.py:668`). #### 8.4.11 Retries and fixed sleeps around Excel (B-R66, B-R68, B-R114)

**What the code does.** Retries: Excel properties five times, two seconds apart (`report_processor.py:178-190`); opening three times on "Call was rejected by callee" (`:195-205`); window activation three times (`:220-227`). Fixed sleeps: 0.5 s after the template copy and after closing (`core/excel_handler.py:125, 180`); five seconds of loading (`report_processor.py:207-211`); 1 s after the window activation and 1 s after each of the first two keys (`:232, 239, 244`); the user's wait time (`:256-258`); up to 5 × 1 s of dialog checks (`:266-275`); `max(10, wait time)` seconds of "extended wait" (`:282-286`); 2 s after saving and 1 s after closing (`:307, 319`); three seconds for file release (`:139-141`) - about 39 seconds per report at the default wait of 10 s, before counting Excel's own start-up (READ (verifier); B-G57).

**Inference.** "Call was rejected by callee" is the message COM gives when Excel is busy (starting up, recalculating, showing a dialog); the comments "Increased from 3 to 5" (`:209`) and "Increased from 0.5" (`:239`, `:244`) show each wait was lengthened after a failure. **HIGH** that these come from real failures; **MEDIUM** that fixed sleeps were chosen because nothing in the keystroke approach can report "ready".

**What it costs today.** Slow runs and no timeouts (B-G57, B-G39). If all three opens are refused, the code carries on with no workbook and still sends the keystrokes (RAN (PQ) `rejected`; B-G62).

### 9.0 How to read this section

This section lists everything project B needs from outside its own 41 files: Python packages, the Python version, the operating system, folders and files on disk, and programs such as Excel - and compares how B is started with the author's Standard 13. Labels, IDs and confidence words are as in 8.0. Extra terms:

- *Package*: an add-on installed into Python with `pip` (Python's package installer). *requirements.txt*: the list `pip install -r requirements.txt` reads. *Declared*: listed there. *Pinned / exact version*: `==3.1.5`; *minimum version*: `>=3.1.2` ("this or anything newer").
- *Wheel*: the ready-made file `pip` downloads for one package, one Python version and one operating system (for example `pywin32-312-cp314-cp314-win_amd64.whl` = pywin32 version 312 for Python 3.14 on 64-bit Windows).
- *Standard library (stdlib)*: the modules that come with Python itself.
- *Transitive dependency*: a package pulled in automatically because another one needs it.
- *pythonw.exe*: the Windows Python that opens no console window. *Console*: the black text window. *excepthook*: a Python hook that receives any error nothing else caught.
- *Current working folder (cwd)*: the folder a program was started "in"; a file opened by a bare name such as `gst_organizer.log` lands there.
- *UNC path*: a network path such as `\\server\share\…`. *8.3 short name*: the old DOS-style short form Windows can give a long path. *Long-path prefix*: `\\?\` in front of a path, which tells Windows to accept paths longer than 260 characters.
- *Embeddable package*: python.org's portable Python that Standard 13 puts in a shared `_runtime` folder.
