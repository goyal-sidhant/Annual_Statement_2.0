- Plain-English terms used below (first use): *worker thread* = a background line of work so the window does not freeze; *signal* = Qt's message from one object to another (here: from the worker thread back to the window); *dict* = a Python table of named entries ("key → value"); *JSON* = a plain-text settings format; *COM* = the Windows mechanism by which Python drives Excel (through the pywin32 add-on); *openpyxl* = a Python library that reads and writes .xlsx files without Excel; *glob* = a wildcard file search such as `*.xlsx`; *regex* / *regular expression* = a text pattern that a name must fit; *HTML* = the text format of web pages, which Qt can show with colours; *UTF-8* = the usual way of storing text with letters of any language; *NTFS* = the Windows disk format; *stem* = a file name without its extension; *mtime* = a file's or folder's "last modified" time; *Level-1 / run folder* = `Annual Statement-<DDMMYY HHMM>`; *Level-2 / client folder* = `<client>-<state code>`; *Version folder* = `Version-<DDMMYY HHMM>`; *category folders* = the three folders inside a Version folder; *variations* = the code's word for problem files; *Links sheet* = the template sheet into which B writes folder paths and file names for the template's own Power Query (Excel's built-in data-import feature).

> **The one thing to keep in mind while reading the flows:** the Python code never reads the *contents* of a client's input file. It reads only the file **name**, the size, the dates and the first 8 bytes (core/file_parser.py:171-215). Every tax figure is produced inside the author's two templates by their Power Query, outside this repository; B only (a) tells the templates where the copied files are (Links sheet), (b) makes Excel refresh them by simulated keystrokes, and (c) copies chosen cells of the refreshed copies into one consolidated workbook.

### 5.1 Category 1 - Input-file recognition (B-R1 to B-R16)

#### B-R1 · Which files the scan looks at
- **Rule:** Only the **top level** of the chosen source folder is searched; sub-folders are ignored with no message. The search asks for `*.xlsx`, then `*.xls`, then `*.xlsm` (a non-recursive glob), drops every name starting with `~$` (Excel's lock files), and sorts the rest by full path. Any error while listing (for example a network folder that has disappeared) returns an empty list, so the user sees "No Excel files found" rather than an error. Other extensions (`.csv`, `.json`, `.xlsb` …) are ignored silently and counted nowhere. On Linux the glob is case-sensitive (`.XLSX` is not found); on Windows Python's glob ignores case (reasoned from Python's behaviour, HIGH). `.xlsm` files are collected but no pattern accepts them (B-R6 to B-R11), so they always end up unrecognised.
- **Exact values:** globs `'*.xlsx'`, `'*.xls'`, `'*.xlsm'`; lock-file prefix `'~$'`; error → `[]`.
- **Where:** utils/helpers.py:249-266 (globs 255-257, `~$` 259-260, sort 262, error 264-266); called at core/file_parser.py:146-152. The same three extensions are typed again at gui/pyqt_main_window.py:469 and in the dead constant utils/constants.py:179 (B-R14).
- **Origin:** globs and sort shared - before the split on 30-10-2025 (edac6a3); the `~$` filter and the removal of the per-file `validate_excel_file` call came in 7e09e5c (B only (after the split)). Before 7e09e5c, files under 1 KB or with a wrong signature were dropped silently here; since then they reach the parser and become variations (B-R2, B-R3).
- **Evidence:** READ; RAN (t1: 15 paths found; `.csv`, `~$` file and sub-folder file never looked at; LT §6.2: `.XLSX` not found on Linux; OF t2).

#### B-R2 · Minimum file size 1024 bytes
- **Rule:** A file smaller than 1024 bytes (1 KB) is not parsed; it goes on the variations list with the issue "File too small to be valid Excel".
- **Exact values:** `size < 1024`; issue text `File too small to be valid Excel`.
- **Where:** core/file_parser.py:181-191. Dead duplicate: utils/helpers.py:231-233 (`validate_excel_file`, never called since 7e09e5c). The unused `EXCEL_SAFETY['verification_size_min']` is a **different value, 10240** (utils/constants.py:222; B-R108).
- **Origin:** in the parser since 7e09e5c (B only (after the split)); the 1024 limit itself existed in `validate_excel_file` from edac6a3 (shared - before the split on 30-10-2025).
- **Evidence:** READ; RAN (t1: a 104-byte file → this variation, and it is left out of "total files"; LT §6.2).

#### B-R3 · Excel signature check (first 8 bytes)
- **Rule:** The first 8 bytes are read; they must start with `PK\x03\x04` (zip package: .xlsx / .xlsm) or `\xd0\xcf\x11\xe0` (old OLE format: .xls), otherwise the file becomes a variation "Invalid or corrupted Excel file". If the file cannot be read: "Cannot read file: <error text>". Nothing beyond these bytes is ever read by Python, so a fake file holding only the header bytes is accepted.
- **Exact values:** read length 8; signatures `b'PK\x03\x04'`, `b'\xd0\xcf\x11\xe0'`; issues `Invalid or corrupted Excel file`, `Cannot read file: <e>`.
- **Where:** core/file_parser.py:193-215. Dead duplicates: utils/helpers.py:235-243 (`validate_excel_file`) and utils/constants.py:182-185 (B-R15).
- **Origin:** in the parser since 7e09e5c (B only (after the split)); same check in `validate_excel_file` since edac6a3 (shared - before the split on 30-10-2025).
- **Evidence:** READ; RAN (LT §6.2: a fake `.xls` with only the header bytes was accepted; a text file named `.xlsx` was rejected).

#### B-R4 · Files whose size and dates cannot be read
- **Rule:** If the operating system cannot report a file's size and dates (for example a broken shortcut), the file is skipped silently: it appears in no list and no count; only the warning `Cannot stat <name>: <error>` reaches the program log. Any other unexpected error for one file is added to the parser's own error list, which nothing outside the parser reads.
- **Where:** core/file_parser.py:174-179; 254-256 (`self.errors`, no reader - grep).
- **Origin:** 7e09e5c (B only (after the split)).
- **Evidence:** READ; RAN (LT §6.2: a broken link dropped silently).

#### B-R5 · How a file name is matched to a pattern · [GST RULE]
- **Rule:** File names are compared with the six patterns **in this fixed order**: GSTR-2B-Reco, ImsReco, GSTR3B, Sales, SalesReco, AnnualReport. Matching ignores letter case, must start at the first character and cover the whole name; the **first** pattern that matches wins. The captured client and state are trimmed of spaces; a part is stored only if it is non-empty before trimming. A file that matches but whose client or state is empty after trimming becomes a variation "Could not parse filename"; a file that matches nothing becomes a variation "No matching pattern found" plus the log warning `Could not parse filename: <name>`. Because every pattern starts with a different fixed word, no name can match two patterns.
- **Exact values:** order as above (dict order of `FILE_PATTERNS`); `re.IGNORECASE`; `.match` + `$`; issues `Could not parse filename` (fallback text) and `No matching pattern found`.
- **Where:** core/file_parser.py:56-124 (loop 77-118, `break` 118, parts 93-102, error 120-122), 228-252; patterns utils/constants.py:13-62.
- **Origin:** shared - before the split on 30-10-2025 (edac6a3; constants.py never changed since).
- **Evidence:** READ; RAN (LT §1.2: 70 names, none matched two patterns; t1).

#### B-R82 · How the mappings become cell reads · [GST RULE] (when in doubt: decides which cell is read)
- **Rule:** (1) When the configuration module is first imported, every mapping whose input sheet **and** input cell are both non-empty is entered as `CELL_MAPPINGS[report type][input sheet][cell] = "<output sheet>_<output column>"` with spaces → `_`, and the label is stored in `FIELD_DISPLAY_NAMES`. Two mappings with the same report type, sheet and cell would overwrite each other (none today); a mapping with an empty sheet or cell is not read but still gets a column. Changing the file needs a restart. (2) For each report, a **second, hidden Excel** opens the refreshed copy (B-R101) and, for the report type (`ITC` reads only ITC_Report files, `Sales` only Sales_Report files), takes each listed sheet by **exact, case-sensitive** name; a missing sheet gives `None` for all its fields (log warning "Sheet '<name>' not found"); otherwise each cell's `.Value` is read (Excel's value: numbers, text, dates or error codes as COM returns them - MEDIUM, not runnable here) and stored **twice**, under the field name and under the bare cell address (e.g. `J15`); a cell that cannot be read gives `None` under both. (3) Every field and value is written to the screen log, the extraction log file and the program log ("✓ <field>: <value>" / "✗ <field>: None"). (4) Any error during reading → no data at all for that report (`{}`).

#### B-R83 · Consolidated value look-up (substring first, exact name second) · [GST RULE]
- **Rule:** For each output column, the consolidator first walks the extracted data **in reading order** and takes the value of the **first field whose name contains the column label** (a case-sensitive text test) - and stops there, even if that value is empty. Labels that contain a space never match a field name (field names use `_`), so they always fall through to the exact field name and show their own configured cells. The one-word labels `IGST`, `CGST`, `SGST` (B-R79, B-R80, B-R81) first match `GSTR-3B_Difference_Diff_IGST` / `_CGST` / `_SGST`, which come first in reading order - so **9 of the 22 columns** show `Diff GSTR-3B` ⚠ J15 / K15 / L15 (template cell positions). The figure written into those columns therefore depends on the order of the extracted data, not on the configured cell. A value of `None` or `''` then becomes "Missing" (B-R88).

### 5.12 Category 12 - Excel handling and safety (B-R96 to B-R110)

COM (Windows' mechanism for one program to drive another) through pywin32 is used in three places: Step 3 report filling (core/excel_handler.py), Step 4 refresh and Step 4 reading (power_query_extractor/core/report_processor.py). None of it could run here; everything is **READ**, with fake-Excel call orders from the reader agents (CU t_fakecom, XL E3-E5, PQ t_pq). How this compares with the author's Standard 12 is Section 8's job; the Standard's line numbers are given only where a rule touches it.

#### B-R96 · Step 3 Excel: attach, hide, always quit
- **Rule:** For each report: `CoInitialize`; first `GetActiveObject("Excel.Application")` - this **attaches to an Excel the user already has open**, if any (log "Using existing Excel instance"); otherwise `Dispatch("Excel.Application")` (log "Created new Excel instance"). On that Excel it sets `Visible = False`, `DisplayAlerts = False`, `ScreenUpdating = False` - so the user's own Excel windows disappear while reports are made, and `Visible` is never set back. The workbook is saved twice (`Save()`, then `Close(SaveChanges=True)`). At the end it sets `ScreenUpdating = True` and `DisplayAlerts = True` (not protected: if Excel has died these raise and the rest of the clean-up is skipped) and then **always calls `Quit()`**, because `self.excel_app` is never set to anything but `None` - the comment "Don't quit if Excel was already open" is not what happens. So an Excel the user had open is closed, with alerts switched back on (MEDIUM what real Excel then does with the user's unsaved workbooks - a hidden "save changes?" prompt or lost work; not testable here). This happens once per report, so twice per client. The `__del__` method that would quit `self.excel_app` never does anything.
- **Exact values:** `GetActiveObject("Excel.Application")`, fallback `Dispatch("Excel.Application")`; `Visible = False`, `DisplayAlerts = False`, `ScreenUpdating = False`; `if self.excel_app is None: excel.Quit()`.
- **Where:** core/excel_handler.py:95-217 (CoInitialize 107; attach 110-115; settings 118-120; save 173, 176; end 203-211; CoUninitialize 213-217), 55 (`excel_app = None`), 57-63 (`__del__`).
- **Origin:** shared - before the split on 30-10-2025 (edac6a3); only bare `except:` clauses were narrowed in c258047 (B only (after the split)), no behaviour change.
- **Evidence:** READ; fake-COM RAN by CU (t_fakecom: `('excel.Quit', 'USER-OWN-EXCEL')`) and XL (E3).
- **Notes:** Standard 12 asks for `DispatchEx`, a hidden Excel with `DisplayAlerts = False`, never taking over the user's own Excel, and `Quit()` in `finally` (rebuild_pipeline_FINAL.md:851-856).

#### B-R99 · Step 4: opening the refreshed copy (refresh and reading)
- **Rule:** (1) The file must exist (`FileNotFoundError`); one byte is read to prove it can be opened (any error re-raised). (2) A workbook with the same full path already open in that Excel is reused. (3) If the path is longer than 218 characters ("Excel's typical limit"): `/` → `\` and the long-path prefix `\\?\` (local path) or `\\?\UNC\` (network path starting `\\`) is added. (4) Attempt 1: `Workbooks.Open(path)`. (5) Attempt 2: close **every** workbook with the same file name in that Excel **without saving**, wait 3 s, open again. (6) Attempt 3: wait 2 s; if Windows gives a different 8.3 short path, open that (if this fails, the message "Could not get short path" is logged and the next step runs); else, if the prefix was added, open the original path; else `Workbooks.Open(Filename=<path>, UpdateLinks=0, ReadOnly=False, IgnoreReadOnlyRecommended=True, Notify=False)`. (7) If everything fails: "❌ All attempts failed. Final error: …"; when the error contains `-2147352567`, advice lines ("File is open in another program", "File is corrupted", "Path is too long (<n> chars)", "OneDrive/SharePoint sync issue", and for long paths "📋 Path length is definitely an issue!" / "Consider enabling long path support in Windows"); the error is raised. `workbook.ReadOnly` is never checked.

### 5.13 Category 13 - Performance and operational constants (B-R111 to B-R114)

#### B-R111 · Background jobs: one thread per kind
- **Rule:** Scanning, processing and extraction each run in their own background thread (a `QThread`, so the window keeps responding); at most **one thread per kind**, so at most three at once. A second job of the same kind is refused silently - only "Scan already in progress" / "Processing already in progress" / "Extraction already in progress" in the program log. Jobs of different kinds can run at the same time (processing and extraction both drive Excel). Closing the window neither stops nor waits for a running job (RAN by MW e11). After a job ends, its thread and worker objects are released (`deleteLater`); a late clean-up can delete a newer running thread and abort the program (RAN by MW e13 with widened timing; LOW likelihood). No widget is touched from a worker thread: results come back by Qt signals.
- **Exact values:** `if self._thread and self._thread.isRunning(): logger.warning(...); return`.
- **Where:** gui/controllers/scan_controller.py:57-94 (guard 59-61); gui/controllers/processing_controller.py:256-298 (guard 259-261); gui/controllers/extraction_controller.py:138-184 (guard 142-144); gui/pyqt_main_window.py:601-608 (close).

### 5.19 Items the registry lacks (UNREGISTERED)

The registry was checked against the code while this section was written. These rule-like items have no registry ID; per the audit conventions they are described here without inventing an ID.

#### UNREGISTERED: Extraction output folder falls back to the target folder · DEAD (in practice)
- **Rule:** The extraction worker takes the run folder it is given; when none is given, its output folder (consolidated workbook and extraction log) is the **target folder itself**. The window never starts an extraction without a run folder (B-R133: "No Level 1 folder available."), so the fallback cannot be reached through the screens.
- **Exact values:** `self.level1_folder = Path(level1_folder) if level1_folder else self.output_folder`.
- **Where:** gui/controllers/extraction_controller.py:28-29; guard gui/pyqt_main_window.py:512-515.
- **Origin:** B only (after the split) (b0e7d0e; c258047 always used the target folder).
- **Evidence:** READ.

#### UNREGISTERED: Every organiser path is built by `safe_path_join`, which drops empty parts
- **Rule:** Run, client, Version and category folders, every copy and the organisation report are joined with `safe_path_join`, which silently leaves out empty name parts and raises `ValueError("No valid path components provided")` when nothing is left. An empty client-folder or file name would therefore not raise an error at the join but put the item one level higher (not reachable with today's recognition rules, which require a non-empty client and state - B-R5; LOW).
- **Exact values:** `valid_parts = [p for p in parts if p]`.
- **Where:** utils/helpers.py:49-64; used at core/file_organizer.py:94, 102, 132, 153, 176, 255, 314.
- **Origin:** shared - before the split on 30-10-2025 (edac6a3).
- **Evidence:** READ.

#### UNREGISTERED: `FileOrganizer.get_summary` · DEAD
- **Rule:** Would report the organiser's counts: `folders_created` as the number of **distinct** folders (`len(set(...))`), `files_processed`, `successful_copies`, `failed_copies`, `skipped_files` (= the rest), `errors`, plus time stamp, mode and target. It is never called. Its distinct count differs from the organisation report's "Folders Created", which counts every append, including the run folder once per client in Fresh mode (B-R40: 6 / 12 / 18 for three clients).
- **Where:** core/file_organizer.py:392-408; compare 345-351.
- **Origin:** shared - before the split on 30-10-2025 (edac6a3).
- **Evidence:** READ (grep: no caller).
